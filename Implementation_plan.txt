# 2. THE HARDCORE CRITIQUE: WHY WE MUST BUILD PHASE 7

A senior engineering architect or VP from Razorpay evaluating Track 03 will examine the system with zero tolerance for fluff. Four critical vulnerabilities remain:

1. **The "Why is this AI?" Critique**:
   * *The Critique*: "You have a 22-D logistic regression predicting baseline $P(\text{recovery})$, but when customer interactions happen in the perception loop (`recovery_agent.ts`), the decision is just `if (dwell > 20s) return SPLIT_PAY`. That is an if-else condition, not an autonomous agent."
   * *The Winning Solution*: **Deterministic Contextual Multi-Armed Bandit (LinUCB)**. Instead of hardcoded rules, an online bandit continuously updates arm parameters based on live reward signals (Net Margin Preserved minus Channel COGS), provably optimizing the exploration-exploitation tradeoff with zero LLM hallucination and sub-millisecond execution.

2. **The "Razorpay Optimizer" Missing Link**:
   * *The Critique*: "In enterprise payment processing, customer communication is the LAST resort. If an HDFC card fails with an acquirer switch timeout (ISO 91 / HTTP 504), Razorpay Optimizer intercepts it in-flight and auto-cascades to Axis/ICICI PG in 1.4s without the customer ever dropping off. Why are you immediately sending an SMS?"
   * *The Winning Solution*: **Tier 0 In-Flight Gateway Cascading Engine**. Seamlessly classifies failures into **Zero-Touch In-Flight Cascade** vs. **Customer-Facing Recovery**. If it's a technical switch drop, cascade in-flight; only if all acquiring rails fail do we trigger customer outreach.

3. **The Live Bank Switch / NPCI Outage Reality**:
   * *The Critique*: "In India, 40%+ of UPI failures are driven by bank core-banking maintenance (e.g. SBI switch downtime). What happens if your recovery tool sends a UPI link for an HDFC account while HDFC's switch has an 18% success rate? It fails again, burning merchant SMS fees."
   * *The Winning Solution*: **Bank Health Circuit Breaker & Inter-Bank Steering**. Wire the already existing `packages/core/src/ingest/rail_health.ts` to live API endpoints and the agent loop. If HDFC UPI is degraded, steer the customer to ICICI/Axis UPI or RuPay Card.

4. **Multi-Domain Dashboard Command Center**:
   * *The Critique*: "Your store frontend has tabs for SaaS and B2B, but your Merchant Dashboard (`dashboard.html`) only displays single D2C checkout metrics. Where is the SaaS Mandate cohort view? Where is the B2B aging ledger and DSO reduction tracker?"
   * *The Winning Solution*: **Executive Multi-Domain Cockpits in `dashboard.html`**. Interactive visual panels for SaaS Mandates (salary morning countdown, RBI compliance counter) and B2B Invoices (aging schedule, 2/10 Net 30 uptake calculator).

## Task 7.1 (`BDT-16`): Deterministic LinUCB Contextual Multi-Armed Bandit

### Objective:
Replace heuristic `if (dwell > 20s)` branching with a mathematically provable, regret-bounded online reinforcement learning bandit that optimizes dynamic intervention choices.

### Mathematical Formulation:
For each decision $t$, observe context vector $x_t \in \mathbb{R}^4$:
1. $x_1 = \min(\text{AmountPaise}, 1000000) / 1000000$ (Standardized ticket size)
2. $x_2 = \min(\text{PriorFailures}, 5) / 5$ (Customer failure history)
3. $x_3 = \min(\text{DwellSeconds}, 60) / 60$ (Portal dwell friction intensity)
4. $x_4 = \text{HistoricChannelResponsiveness} \in [0, 1]$

For each action arm $a \in \mathcal{A}$ where $\mathcal{A} = \{\text{UPI\_INTENT}, \text{WHATSAPP\_UTILITY}, \text{SPLIT\_PAY\_3X}, \text{DOWNSELL\_5PCT}\}$:
Maintain design matrix $A_a \in \mathbb{R}^{4 \times 4}$ (initialized to $I_4$) and reward vector $b_a \in \mathbb{R}^4$ (initialized to $\mathbf{0}$).

Compute point estimate $\hat{\theta}_a = A_a^{-1} b_a$ and select arm:
$$\hat{a}_t = \arg\max_{a \in \mathcal{A}} \left( x_t^T \hat{\theta}_a + \alpha \sqrt{x_t^T A_a^{-1} x_t} \right)$$
where exploration parameter $\alpha = 0.2$.

### Feedback Reward:
Upon settlement or dunning expiration:
$$r_t = \frac{\text{Net Margin Won} - \text{Channel COGS}}{\text{Ticket Amount}} \in [0, 1]$$
Update step:
$$A_{a_t} \leftarrow A_{a_t} + x_t x_t^T, \quad b_{a_t} \leftarrow b_{a_t} + r_t x_t$$

### Key Guarantees:
- **Zero non-determinism**: Given historical matrix $(A_a, b_a)$, arm selection is an exact analytical calculation.
- **Sub-millisecond execution**: Inverting a $4 \times 4$ matrix takes $<0.05\text{ms}$.
- **Provable convergence**: $O(\sqrt{KT \ln T})$ regret bound.

- `packages/core/src/agent/contextual_bandit.ts`
- `packages/core/src/agent/recovery_agent.ts`
- `tests/core/contextual_bandit.test.ts`

## Task 7.2 (`OPT-17`): Razorpay Optimizer Tier-0 In-Flight Gateway Cascade Engine

### Objective:
Emulate enterprise Razorpay Optimizer multi-gateway cascading to resolve technical acquirer errors in-flight ($<1.8\text{s}$) before declaring a payment failure or disturbing the customer.

### Implementation Blueprint (`packages/core/src/executor/gateway_optimizer.ts`):
- **Gateway Cascade Table**:
  - Primary Acquirer: `HDFC_SMARTGATEWAY`
  - Secondary Acquirer: `AXIS_PG`
  - Tertiary Acquirer: `ICICI_PAYSEAL`
- **Trigger Conditions**:
  - `ISO-8583 Code 91` (Issuer switch inoperative)
  - `ISO-8583 Code 96` (System malfunction)
  - `HTTP 504 Gateway Timeout`
  - `NETWORK_TIMEOUT`
- **Execution Workflow**:
  1. Receive payment request.
  2. Attempt Primary PG.
  3. If technical failure and latency $<2000\text{ms}$:
     - Fire synchronous failover to Secondary PG with same `idempotency_key`.
     - Log `IN_FLIGHT_CASCADE_SUCCESS` in SHA-256 audit ledger.
     - Return HTTP 200 `CAPTURED` to merchant store.
  4. If all acquirers in cascade fail or failure is customer-side (`INSUFFICIENT_FUNDS`, user cancellation):
     - Transition to ARBITER FSM `DETECTED` for customer outreach.

### Target Files:
- `packages/core/src/executor/gateway_optimizer.ts`
- `app/server.ts`
- `tests/core/gateway_optimizer.test.ts`
